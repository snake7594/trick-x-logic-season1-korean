# Trick × Logic Season 1 — 한글 패치

PSP 추리 어드벤처 **트릭 × 로직 시즌 1**(UCJS-10097)의 한국어 패치입니다.
본문·대사 **20,524건 전량**과 일본어가 들어간 **이미지 222장**을 한글화했습니다.

패치는 **xdelta 차분 파일**로 배포합니다. 게임 데이터는 들어 있지 않으므로
**원본 UMD 이미지를 직접 준비**하셔야 합니다.

> 최신 패치: [Releases](../../releases/latest)

## 1. 패치 적용 방법

### 1-1. 준비물

| | |
|---|---|
| 원본 ISO | `Trick x Logic Season 1.iso` — **718,307,328 바이트** |
| 패치 파일 | `TrickxLogic_S1_Korean_v1.6.0.xdelta` ([Releases](../../releases/latest)) |
| 패치 도구 | xdelta3 — [공식 배포처](https://github.com/jmacd/xdelta-gpl/releases) |

Windows에서는 GUI 도구인 **xdeltaUI**(`xdelta UI` / `Delta Patcher` 등 아무거나)를
써도 되고, 명령줄 `xdelta3.exe` 를 써도 됩니다.

### 1-2. ⚠ 먼저 원본 ISO 가 맞는지 확인하세요

**해시가 다르면 패치가 실패하거나, 성공해도 게임이 깨집니다.**

```
파일 이름   Trick x Logic Season 1.iso   (이름은 달라도 됩니다)
크기        718,307,328 바이트
MD5         4D27B0FCCCE2EAAB86E992D8127C77AC
SHA-1       58E56644F585928FB584C0304767069E827D87A1
SHA-256     EFE2A0EEAE09C3888E5C58EE6E8E03609AF6033B8B5FC39235BD81034FC2FA52
```

확인 방법:

```bash
certutil -hashfile "Trick x Logic Season 1.iso" MD5
```

```bash
md5sum "Trick x Logic Season 1.iso"
```

`.cso` 로 압축된 파일은 **패치할 수 없습니다.** 먼저 `.iso` 로 되돌리세요.
ISO 를 다시 굽거나 재패킹한 것도 해시가 달라져 안 됩니다. **UMD 원본을 그대로
덤프한 것**이어야 합니다.

### 1-3. 패치하기

**명령줄 (Windows / macOS / Linux 공통)**

```bash
xdelta3 -d -s "Trick x Logic Season 1.iso" "TrickxLogic_S1_Korean_v1.6.0.xdelta" "Trick x Logic Season 1 (KR).iso"
```

- `-d` 디코드(적용) · `-s` 원본 파일 · 마지막이 만들어질 한글판입니다.
- 예전 xdelta 1.x 실행 파일(`xdelta.exe`)도 같은 인자를 씁니다.

**GUI (xdeltaUI)**

1. `Apply Patch` 탭을 엽니다
2. `Patch` 에 `.xdelta` 파일
3. `Source File` 에 원본 ISO
4. `Output File` 에 만들 한글판 ISO 이름
5. `Patch` 버튼

### 낭독 스태프롤 — 세로쓰기 350 글줄

`stuff_credit_01`~`32` 32종(아카이브 4개에 같은 그림이 들어 있어 파일로는 128장)에
집필진·성우·제작진 크레딧이 **세로쓰기**로 들어 있습니다. `atlas.boxes_v` 로 글줄
상자를 411개 뽑고, 이름 하나가 성·이름으로 갈라진 자리를 손으로 묶어 350 글줄로
정리했습니다. 가로획만 있는 `一`·`二` 는 상자 판정(`minh=14`)에서 빠지므로, 상자가
놓친 덩어리 중 **높이 4px 이상**인 것만 다시 붙였습니다(높이 3px 은 `【 】` 괄호 획
이라 남겨 둡니다).

한글 음차는 한자보다 글자 수가 많아 그대로 두면 글자가 작아집니다(`아리스가와
아리스` 9칸 vs `有栖川有栖` 5칸). 그래서 **같은 열에서 아래로 빈 만큼** 상자를 늘려
원래 글자 크기를 지켰습니다. 아래 글줄과 `【 】` 괄호는 넘지 않습니다. 그래도 안
들어가는 배역 이름표(`【九条薫】`·`【丸ノ内慶次】`)는 이름표와 같은 짧은 이름
(`카오루`·`마루노우치`)으로 넣었습니다.

이 그림들은 **바탕이 완전 투명**(`255,255,255,0`)이라 지울 배경색이 없습니다.
`erase_box_v` 는 상자 좌우 3px 를 배경 표본으로 삼는데 거기가 글자 그늘(검정·알파
10~30)이라 상자가 통째로 뿌옇게 칠해졌습니다. 그래서 `clear-v` 종류를 따로 만들어
**투명하게 비우고**, 원본과 같은 모양(연회색 획 183 + 검은 테 + 알파 45% 로 흐린
검은 번짐)으로 다시 그립니다.

### ⚠ 길이 접두사가 없는 문자열 — 추출에서 통째로 빠져 있었다

대사(op 0x01)는 `u32 길이 + cp932 + NUL` 이지만, 추리에 쓰는 데이터에는
**길이 없이 NUL 로만 끝나는** 문자열이 따로 있다. 추출 도구가 이걸 못 봐서
**6,770건**이 일본어로 남아 있었다.

그중 **키워드 이름**은 게임 진행을 막는다. 게임은 분홍 글자를 눌러 얻은
키워드를 `*_question.bin` 안의 문자열과 **글자 그대로** 대조하기 때문에,
본문만 한국어로 바꾸면 정답 조각을 골라도 추리가 진행되지 않는다.

    분홍 범위의 글자 - 제어 태그(㊤㊥㊦㊧㊨) = 키워드 이름

`tools/keyname.py` 가 본문에서 그대로 떠 와 맞춘다(784건). 사람이 따로
번역하면 한 글자만 달라도 안 맞으므로 반드시 기계로 뽑아야 한다.

수수께끼·착상·힌트 제목과 조서 인물명 414건은 `text/rawtext.json` 에
따로 번역해 두고 같은 도구가 넣는다. **추리 데이터(`*_question.bin`
`*_inspiration.bin` `*_hint*.bin` `*_report.bin` `*_answer_data.bin`)에
남은 일본어는 0건**이다.

남은 것을 다시 세어 보니 **678건 / 555종**이었다(앞서 「약 5,600건」이라고
적은 것은 한국어를 한자 코드로 넣은 것을 일본어로 잘못 센 결과다).
그중 **311종은 정렬용 히라가나 읽기**라 화면에 안 나오고, 실제 번역 대상은
**244종**이었다 — 용어 해설 81, 조서 문항 40, BGM·아카샤 지명 37, 포기 화면 30,
힌트 제목 25 등. 전부 `text/rawtext.json` 에 넣었다.

**스크립트 전체에 남은 일본어(읽기 제외)는 0건**이다.

#### 검증기가 걸렸던 것 — 가짜 문자열

적용 범위를 넓히자 8개 파일에서 문자열 개수가 하나씩 늘어난 것으로 잡혔다.
넣은 한국어 원시문자열 **앞 4바이트가 우연히 길이 필드처럼 보여**
`find_strings` 가 한 번 더 잡은 것이다(op 0x3c 등).

    FW_marunouchi.bin  원본 221 vs 신규 222
    「마루노우치의 추리와 어긋나는 현장 상황은？」 이 op=0x3c 로 잡힘

위치로 zip 하면 그 뒤가 통째로 밀린다. `verify_strict.align` 이 **원본의
오프코드 순서**를 기준으로 신규를 따라가며 남는 것만 건너뛴다. 이렇게 하니
23,243개 전부 대조되고 불일치 0 이다.

### 한자 읽기(루비) 제거 — `tools/ruby.py`

본문 문자열 사이에 이런 짝이 들어 있다.

    op 0x32  u32 payload길이  [ u32 덮는글자수 | <읽기 cp932> NUL ]
    op 0x01  u32 길이         <읽는 대상 글자> NUL
    op 0x33  00 00 00 00

한국어 본문 위에 일본어 가나가 그대로 떠서 지워야 한다. 짝 구조를 건드리면
위험하니 **읽기 글자를 전각 공백으로 바꾼다**. 명령을 통째로 빼면 뒤따르는
`0x33` 이 짝을 잃는다.

처음에는 `32 09 00 00 00` 이라는 **바이트열을 찾았는데**, 이건 payload 길이가
정확히 9(가나 두 자)인 것만 걸립니다. 명령 단위로 다시 세니 전체가 **561개**였고
128개만 지우고 있었습니다.

또 하나: payload 앞 u32 는 「덮는 글자수」가 아니라 **읽기 개수**입니다. 한
명령에 둘 이상 들어 있는 자리가 있어서(`ろ` + `けん`), 하나로 보고 통째로
읽으면 가운데 NUL 때문에 가나 판정에 걸려 그냥 지나쳤습니다. 지금은
**577개**를 바꿉니다.

#### ⚠ 빈 문자열로 두면 소설 읽기 화면이 멈춘다

처음에는 읽기를 **빈 문자열**로 만들었다(NUL 만 남김). 그랬더니 소설 읽기
화면이 **첫 루비에서 멈췄다** — 제1장 제목 다음 쪽, `TU.bin` 블록 1 의
`えつらん` 이 게임이 처음 만나는 루비다. 길이 0 인 읽기를 해석기가 감당하지
못하는 것으로 보인다.

가나는 cp932 에서 모두 2바이트이고 전각 공백도 2바이트다. 그래서 지금 방식은
**payload 길이가 1바이트도 안 변하고**(561개 전부 원본과 동일) 명령 구조도
그대로다. 글자 폭이 같아 배치도 안 흔들리고, 화면에는 아무것도 안 보인다.

### 챕터 제목 앞의 전각 공백

원문 챕터 제목은 `　　　第一章` 처럼 **앞에 전각 공백**을 두어 세로쓰기에서
위치를 잡는다. 번역이 이 공백을 지우고 뒤에 붙이는 바람에 제목이 원본 2열에서
3열로 넘쳤다. 78건을 원문과 같은 앞 공백·같은 칸 수로 되돌렸다.

### 조각 이음매의 띄어쓰기 — `tools/joints.py`

번역이 조각(op 0x01) 단위로 이뤄져 이음매의 공백이 빠진다. 예전 `spacefix.py`
는 규칙만 있고 **파이프라인에 안 들어가 있어서** 한 번 돌리고 만 상태였다.

어떤 조각끼리 화면에서 이어 붙는지는 JSON 순서만으로는 알 수 없다. 명령
스트림을 걸어 사이에 끊는 명령이 있는지 본다. **어떤 명령이 끊는지는 원문
문장부호와의 상관으로 가려냈다** — 명령 없이 붙은 1,532쌍 중 앞 조각이
`。！？` 로 끝나는 비율은 9.0%(기준선)인데, 아래 명령이 끼면 25~94% 로 뛴다.

    29 94% · af 73% · 19 63% · 0f 63% · 39 62% · 38 61% · 57 55%
    aa 55% · 6d 46% · 6c 45% · 27 43%(줄바꿈) · 28 25%(입력 대기)
    반대로 루비(32·33)는 2.7%·0.0% — 확실히 같은 줄 안이다

조사인지 관형사인지도 한국어만 봐서는 못 가른다. `'추리 파일'+'을 열어'`(조사)
와 `'그 책은'+'이 명계에서'`(관형사)가 같은 모양이다. **원문을 본다** — 뒤
조각의 일본어가 `を·が·は…` 로 시작하면 붙이고, 앞 조각이 `、` 로 끝났으면
띄운다. 여는 따옴표 앞도 띄운다(`명계에서『아카샤』`).

이렇게 **805곳**을 고쳤다. 낱말이 조각 경계로 쪼개진 자리(`여리`+`고`,
`끔찍`+`한`)와 루비로 쪼개진 자리(`絨`/`毯`)는 제외한다 — 여기에 공백을 넣으면
낱말이 깨진다. 하단 안내바(`information_message.bin`)는 설명과 버튼 이름이
각각 다른 칸에 그려지므로 건드리지 않는다.

**마침표는 대부분 원문에도 없다.** 한국어 문장이 끝났는데 부호가 없는 조각이
4,822개인데 그중 4,819개는 일본어 원문에도 부호가 없다 — 이 게임의 문체다.
원문에 있는데 번역에서 빠진 것만 고쳤다.

### 자료 도면 라벨 — `tools/snap.py`

`file_figure_*` (사건 현장 도면·지도) 13종의 방 이름·가구·거리 표시 **136개**를
옮겼습니다. 도면은 추리에 직접 쓰이는 자료입니다.

라벨의 절반은 **판 없이 도면 위에 얇게 얹힌 흰 글자**라 전역 임계값으로는
안 잡힙니다. `snap.py` 에 대충 찍은 영역을 주면 상자 안에서만 밝기를 갈라
글자 경계로 좁혀 줍니다. 상자를 눈대중으로 넓히면 옆 벽선·화살표까지
지워지므로 좌표는 반드시 이렇게 재야 합니다.

함정이 둘 더 있었습니다.

1. **상자가 글자에 딱 붙으면 글자와 바탕이 뒤집힌다.** 상자 안이 흰 획으로
   가득 차서 `local_ink` 가 흰 글자를 바탕으로, 갈색 방을 글자로 본다. 결과가
   흰 판에 갈색 한글이었다(`厨房`·`講堂`). 지도에 `'ring'` 을 적으면 **상자
   둘레**(정의상 바탕)와 견줘 더 먼 쪽을 글자로 잡는다. 판 위 흰 글자
   (`車で1時間`)도 같은 규칙으로 맞는다.
2. 획의 안티에일리어싱 가장자리가 배경 표본으로 뽑히면 **열 하나가 통째로
   어둡게 칠해져 세로 막대**가 생긴다. `'ring'` 일 때 제외 마스크를 2px 로
   부풀려 막았다.

`'ring'` 은 지도에서 그 상자에만 켜는 표시라 다른 이미지 180장은 한 화소도
바뀌지 않습니다(전/후 비교로 확인). 밝기로 자동 판정하게 넓혔더니 인물
프로필 이름표가 회색으로, 낭독 화면 제목에 회색 띠가 생겨서 손으로 켜는
쪽을 골랐습니다.

도면 위의 흐릿한 배경 지명(`保田谷町` 등 원본에서도 읽기 어려운 것)은
남겼습니다. 지우면 지도 질감이 깨집니다.

### 남은 일본어 — 전수 점검 결과

최종 ISO 의 스크립트를 훑어 **가나가 남은 곳은 0건**입니다(`づ` 로 잡히는
11건은 좌표 바이트 `82 c3` 가 우연히 디코드된 오탐).

여기까지 오는 데 두 가지가 더 걸렸습니다.

- `keyname` 이 **통히라가나 문자열을 무조건 정렬용 읽기로 보고 건너뛰었다.**
  `どてら` 처럼 화면에 나오는 낱말이 번역표에 있는데도 빠졌습니다. 이제
  **번역표를 먼저 보고**, 거기 없을 때만 읽기로 취급합니다.
- 루비 payload 의 u32 가 읽기 **개수**라는 걸 뒤늦게 알았습니다(위 참고).

번역하지 않는 이미지는 30장입니다 — 제작사 로고·빈 패널·무늬, 그리고
**아트 컬렉션(제작 스케치)**. 스케치의 손글씨 메모까지 고치면 그림이 망가지므로
원본 그대로 둡니다.

## 3. 개발 내역

### 3-1. 파일 구조 해석

ISO9660 안에 `TU.bin` `NF.bin` … 같은 **SECTPACK** 아카이브가 들어 있습니다.

```
SECTPACK  이름\0 + u16 id(bit15=압축) + u16 시작섹터 + u16 섹터수
          데이터 시작 = ceil(TOC끝 / 2048)
압축      커스텀 LZ77 — 제어 바이트 MSB 우선, 1=리터럴
          len = (b0 & 0x0F) + 3,  dist = ((b0 >> 4) << 8) | b1
스크립트  PRCS — 0x10 헤더 뒤로 `u8 명령 + u32 payload 길이 + payload` 반복
          op 0x01 = 대사(payload 가 곧 cp932 + NUL), 0x0f = 라벨(화면 한 페이지 경계)
폰트      SIR0 컨테이너 + varint 포인터 목록
```

### ⚠ 여기서 게임을 죽였습니다 — 명령의 payload 길이 필드

처음에 **「파일 내 절대 오프셋 참조가 없으니 번역문 길이를 자유롭게 바꿔도
된다」**고 적었습니다. 오프셋 참조가 없는 건 맞습니다. 하지만 **명령마다 payload
길이 필드가 있다는 것을 찾아보지 않았습니다.**

대사는 payload 가 문자열 하나뿐이라 u32 가 곧 문자열 길이입니다. 그래서 대사만
바꿀 때는 구조를 몰라도 맞아떨어졌습니다. 그런데 추리 데이터의 **길이 접두사 없는
문자열**은 한 명령의 payload 안에 여러 개가 묶여 있습니다.

```
0x15   a4  31 00 00 00   "ENV_NF\0前奏曲第２番\0Ｇ．ガーシュウィン\0env_q_b01\0"
                         └─ 정확히 0x31 = 49 바이트
0x4b   a4  3f 00 00 00   ...                       ← 다음 명령이 정확히 여기
```

안에서 길이가 바뀌었는데 **감싸는 명령의 u32 를 안 고쳐서** 해석기가 그 뒤로
엉뚱한 곳을 명령으로 읽었습니다. `keyname` 이 건드린 80개 중 **75개**, `ruby` 가
건드린 **13개 전부**가 그렇게 깨졌고, 그중에 부팅 초기화 스크립트
`sn7_init.bin` 이 있어서 **v1.0.3 ~ v1.0.10 은 게임이 시작조차 못 했습니다.**

`tools/prcswalk.py` 가 명령 스트림을 처음부터 끝까지 걸어 파일 끝에 정확히
도착하는지 봅니다(원본 243개 전부 통과). 문자열을 갈아 끼울 때 감싸는 명령의
길이도 같이 고칩니다. `verify_strict.py` 가 이 검사를 함께 하므로 **문자열이 다
맞아도 길이가 어긋나면 잡힙니다** — 이번 버그는 문자열 대조로는 안 잡혔습니다.

### 3-2. 한글 글리프가 없다 → 한자 코드 자리에 그려 넣기

게임 폰트에는 한글이 한 글자도 없습니다. 코드 표를 새로 짜면 배정되지 않은 한자가
흰 박스로 나와서, **원본 한자 코드(0x889F~)를 그대로 쓰고 그 자리에 한글을 렌더링**
했습니다. 쓸 수 있는 슬롯 1,847개 중 1,207개를 썼습니다.

새 글자가 번역에 등장하면 폰트를 다시 만들어야 합니다
(`mapping.py` → `build_font_kr.py`).

### 3-3. 대사가 문장이 아니라 조각으로 쪼개져 있다

루비·강조·키워드 표시 때문에 한 문장이 여러 문자열로 나뉘어 있습니다.
`prologue` 는 조각의 76%가 6자 이하입니다. 조각별로 번역하면 문장이 망가지므로
**문장 그룹(11,468개) 단위로 번역한 뒤 조각에 나눠 담았습니다.**

이 과정에서 조각 이음매의 띄어쓰기가 사라지는 문제가 생겨, 조사·어미 규칙으로
판정하는 `spacefix.py` 를 만들어 **5,517곳**을 고쳤습니다.

또 하나의 함정: **낱말이 조각 경계를 넘어가면 분홍 키워드 이름이 망가집니다.**
조각 경계를 원문과 맞출 필요는 없지만, 분홍 범위에 걸친 조각은 다르다 —
그 범위의 글자가 곧 키워드 이름이기 때문입니다. 「ウコンが置いてある」의
「ウコン」이 앞 조각으로 넘어가면 키워드가 「이 놓여 있으니까」가 됩니다.
678종을 전수 점검해 19종을 앞뒤 조각과 함께 다시 나눴습니다.

### 3-3-1. 외곽선 — 네 번 헛짚었다

게임은 글리프 알파를 그대로 그리는데, **가장자리의 중간값이 검은 외곽선**으로
보인다. 원본 한자 획 단면이 `7 F 7` 인 것이 그 증거다.

| 시도 | 결과 |
|---|---|
| 굵게(`BOLD=1.55`) | 흰 획만 두꺼워지고 외곽선은 그대로 |
| 0/15 이진화 | 중간값이 없어져 **외곽선 소멸** |
| 속 F + 테 7 조립 | 계조가 없어 거칠고, 획 사이 빈 곳까지 테로 메워 **외곽선이 안으로 파고듦** |
| 전체 감마 | 계조는 살았지만 속까지 낮아져 **너무 얇아짐** |
| **속은 꽉 + 가장자리만 감마** | 두께·계조·외곽선이 함께 산다 |

```
덮개 0.5 이상 -> 15 (흰 속)      그 아래는 감마로 낮추되 **최소 RIM(8)**
```

`RIM` 이 외곽선 진하기다. 바닥을 안 깔면 가장자리 값이 1~3 까지 흩어져
외곽선이 희미해진다. 원본 한자는 7 이고, 여기서는 한 단계 올린 8 로 깐다. 모든 가장자리가 확실한
외곽선이 된다. **흰 속은 그대로**다.

|  | 테(4~9) | 희미(1~3) | 속(≥C) |
|---|---|---|---|
| 원본 한자 | 37.5% | 21.0% | 29.1% |
| 바닥 없음 | 15.7% | 13.8% | 62.7% |
| **RIM 8** | **33.8%** | **0%** | 58.9% |

그래도 획이 픽셀 격자에 딱 맞는 자리는 덮개가 0 에서 바로 1 로 튀어
중간값 화소가 안 생긴다 — 거기서 외곽선이 끊긴다. 그래서 **덮개가 0 인
자리**가 속에 붙어 있으면 거기에도 `RIM` 을 넣어 테를 이어 준다.

    ...........77777.
    ..7FFFFFFFFFFFF7.     속(F)은 그대로, 테(7)가 끊기지 않는다
    ..7FF777BFB99FF7.     글자 화소(8~E)도 안 건드린다

**글자 화소(덮개 > 0)는 건드리지 않으므로** 예전처럼 획 안으로 파고들지
않는다. 1px 짜리 속 빈 곳이 테로 메워지는 것은 원본 한자도 마찬가지다.

⚠ `GAMMA` 를 올리면 외곽선이 **희미해진다**(값이 내려가므로). 진하게 하려면
`RIM` 을 올려야 한다. 전에 이 문서에 반대로 적어 뒀다.

한 글자가 칸에서 차지하는 잉크 양으로 두께를 쟀다.

| | 잉크 |
|---|---|
| 속 F + 테 7 (EB) | 0.391 — 너무 굵다 |
| 전체 감마 (B γ1.4) | 0.167 — 너무 얇다 |
| **지금 (B · CORE 0.5 · γ1.2)** | **0.326** |

굵기는 **Bold** 다. 이미지(GIM) 쪽은 크게 그리므로 ExtraBold 그대로다
(`paths.TTF` / `TTF_GAME`).

### 3-3-3. 대사창 2줄 — `tools/advfit.py`

대사창 글자 영역은 화면에서 재서 **342px**(x70..412)이다. 계산과 맞는다.

    16글자×17 + 6공백×11 = 338px   ← 실제 첫 줄 폭

소설 읽기 화면(민짜 `TU.bin` 등)은 여러 줄이 정상이라 빼고, **원문이 2줄에
들어가는 것만** 대상으로 본다 — 원문도 넘치는 자리는 애초에 2줄 화면이 아니다.

처음 잰 값은 **102건**이었다. 번역이 중복된 곳(`…볼 수 있겠네요` +
`그렇게 생각할 수 있겠지`)이 여럿이라 고치니 자연히 짧아졌다. 나머지는 한두
글자씩 줄였고, `전……9일` 처럼 **말줄임표가 낱말을 붙여 버려 줄바꿈이 낭비되는**
자리는 띄어쓰기로 풀었다(381곳).

지금 **2줄 초과 0건**이다.

### 3-3-2. 띄어쓰기 폭 — 글리프의 진행 폭만 줄인다

게임은 **비례 폭**으로 그리고 진행 폭은 글리프 헤더의 `x1`(rec[8])이다.
화면에서 글자 시작 위치를 재 보면 헤더 값과 정확히 맞는다.

    피(144) → 손(306)   4글자+공백 = 81px    4×17 + 13
    끝(430) → 유(520)   2글자+공백 = 45px    2×17 + 11
    댄(644) → 건(702)   1글자+공백 = 29px    1×17 + 12
                        → 글자 17px, 공백 11px

그래서 **문자를 반각으로 바꿀 필요가 없다.** 전각 공백(0x8140) 글리프의 진행
폭만 줄이면 된다(`build_font_kr.SPACE_ADV`). 텍스트도 스크립트도 한 바이트
안 바뀌므로 「반각 문자를 넣으면 오작동한다」는 위험이 아예 없다.

    NovelFont 12 -> 7,  AdvFont 11 -> 6   (반각 공백은 9 / 8)

반각(9/8)이 실기에서 정상 동작하는 것을 확인한 뒤 더 좁혔다. 같은 문장 폭이
293 -> 268px 로 줄어 한 줄에 1~2글자가 더 들어간다.

### 3-4. 반각 문자를 쓰면 실기에서 죽는다

원문이 한 번도 쓰지 않는 문자(반각 공백, `,`, `.`, `'`)를 넣으면 게임이 오작동합니다.
전각으로 바꿔서 넣습니다(`　` `、` `。` `『』`). 제어 태그 `㊤㊥㊦㊧㊨` 도
개수·순서를 원문 그대로 유지해야 하며, 지우면 게임이 멈춥니다.

### 3-5. 이미지 — GIM 텍스처 1,064장

전부 PNG 로 뽑아(실패 0) 일본어가 든 것을 골라 다시 그렸습니다.

가장 오래 붙잡았던 버그: **픽셀 데이터 시작 오프셋은 `+0x1C` 이고 헤더 크기(`+0x18`)와
다릅니다.** 헤더 크기 뒤부터 읽으면 16바이트 앞서 읽어 이미지 전체에 가로 줄무늬가 생깁니다.
`pitch = ceil(w*bpp/8/16)*16`, `height = ceil(h/8)*8` 정렬과 PSP 표준 swizzle(16B×8행)도
같이 맞춰야 합니다.

512×512 아틀라스는 스프라이트가 빽빽해서, 한글이 길다고 상자를 늘리면 **옆 칸을 덮어써
엉뚱한 화면에 한글 조각이 나타납니다.** 실제로 스토리 선택 화면에 `께`·`이` 가 튀어나온
적이 있어, 상자를 원본 글자 범위 안으로 고정하는 규칙을 세웠습니다.

### 3-6. 분홍색 키워드 위치표 재계산

추리에 쓰는 본문 조각(화면에서 분홍색)의 위치가 `*_keyword.bin` 에 **글자 인덱스**로
적혀 있습니다. 번역으로 문장 길이가 바뀌면 이 표도 같이 고쳐야 하고, 안 고치면 엉뚱한
글자가 분홍색이 되거나 **범위를 벗어나 실기에서 멈춥니다.**

```
u32 count      # 스크립트 블록 수
u32 0
레코드 × count # 블록 순서 그대로 1:1. 첫 블록(제목)은 제외
  type 0 : u32 0                                 # 분홍 글자 없음
  type 1 : u32 1, u8 cnt, u16 pad, u8 seg,
           cnt × { u8 start, u8 end, u32 pad }   # end 포함
```

함정이 둘 있었습니다.

1. **블록마다 레코드가 하나씩** 있습니다(키워드가 없으면 4바이트짜리). 이걸 모르면
   레코드가 한 칸씩 밀립니다.
2. 게임이 세는 인덱스에는 **줄바꿈 명령(`27 01 00 00 00`)마다 한 글자가 더**
   들어갑니다. 그 차이 δ 는 **레코드가 아니라 범위마다** 누적됩니다. 레코드당 δ
   하나로 보면 50개가 어긋납니다.

   (처음에는 δ 가 한자 읽기(루비)에서 온다고 적었는데 **틀렸습니다.** 범위 앞의
   `27 01 00 00 00` 개수를 세어 보니 682곳 중 681곳이 -δ 와 정확히 같았습니다.
   덕분에 루비를 지워도 키워드 위치는 흔들리지 않는다는 것을 확인했습니다.)

δ 를 만드는 요소는 번역이 건드리지 않으므로, **조각 경계에서의 한·일 길이 차이만큼만
밀어** 주면 δ 가 저절로 보존됩니다. 430 레코드 / 682 범위 전부 조각 경계에 정확히
맞는 것을 확인했습니다.

### 3-7. ISO 크기를 원본과 똑같이 유지

번역으로 스크립트가 25섹터 늘었지만, ISO 파일 사이의 여유 섹터로 흡수했습니다.
`SI_A.bin` 뒤에 여유가 없는 `BH.bin` 만 1섹터 뒤로 옮기고 ISO 디렉터리 레코드의
LBA·크기를 little/big endian 양쪽 다 갱신했습니다.

`NovelFontList.dat` 은 원본이 **무압축**이라, 압축해 넣을 때 SECTPACK TOC 의 압축
플래그(`id |= 0x8000`)를 같이 켜지 않으면 게임이 압축 헤더를 SIR0 로 읽어 폰트가 깨집니다.

### 3-8. 검증

```
총 문자열 23,243
  번역 반영 정확 20,524
  비번역 원본유지 2,719
  불일치 0 / 파일 개수 불일치 0
분홍 범위 682개 / 블록 밖 0개
```

빌드한 ISO 를 다시 뜯어 **모든 문자열을 원문·번역문과 바이트 단위로 대조**합니다
(`verify_strict.py`). 배포한 xdelta 는 실제로 적용해서 SHA-256 이 일치하는 것까지
확인했습니다.

## 5. 직접 빌드하기

원본 ISO 하나만 있으면 이 저장소만으로 한글판을 **똑같이** 다시 만들 수 있습니다.

### 5-1. 준비

```bash
pip install pillow numpy scipy
```

원본 ISO 를 저장소 루트에 `Trick x Logic Season 1.iso` 로 두거나, 환경 변수로 알려 줍니다.

```bash
export TXL_ISO="/path/to/Trick x Logic Season 1.iso"
```

```powershell
$env:TXL_ISO = "D:\games\Trick x Logic Season 1.iso"
```

### 5-2. 빌드

중간 산출물이 **현재 폴더**에 쌓이므로 빈 폴더를 만들어 그 안에서 돌립니다.

```bash
mkdir build && cd build
python ../tools/bootstrap.py        # ISO -> common.bin, 원본 폰트
python ../tools/mapping.py          # 한글 -> 한자 코드 배정
python ../tools/build_font_kr.py    # 한글 폰트 굽기
python ../tools/insert.py           # 번역문 재삽입
python ../tools/keywordfix.py       # 분홍 키워드 위치 재계산
python ../tools/build_images.py     # 이미지 한글화
python ../tools/build_iso.py        # ISO 조립
python ../tools/verify_strict.py    # 검증
```

`엄밀 검증 통과` 가 나오면 성공입니다. 결과는 저장소 루트에
`Trick x Logic Season 1 (KR).iso` 로 만들어지고, SHA-256 이 위 1-4 절의 값과 같습니다.

### 5-3. 배포용 xdelta 만들기

```bash
xdelta3 -e -f -s "Trick x Logic Season 1.iso" "Trick x Logic Season 1 (KR).iso" patch.xdelta
```

## 6. 번역을 고치고 싶다면

1. **[text/CODEX.md](text/CODEX.md) 를 먼저 읽으세요.** 지키지 않으면 게임이 죽는
   규칙들이 있습니다(반각 문자 금지, 제어 태그 유지, 조각 경계 띄어쓰기 등).
2. `text/*.json` 의 `ko` 필드를 고칩니다. `loc` 은 재삽입 좌표이므로 **수정 금지**입니다.
3. 검사합니다.
   ```bash
   python text/validate.py
   ```
4. 5-2 의 빌드를 다시 돌립니다. 번역에 **새 한글 글자**가 등장했다면 `mapping.py`
   부터 다시 돌려야 폰트에 그 글자가 들어갑니다.

이미지 문구는 `images/image_text.json` 과 `tools/atlas_maps.py` 를 고친 뒤
`build_images.py` 부터 다시 돌립니다. 자세한 방법은 [images/README.md](images/README.md).

  지금 글자가 이미 그 한계까지 차 있어(원본 일본어보다 큽니다) 더 키우면 테두리를
  넘어갑니다.
